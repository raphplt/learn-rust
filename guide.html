🏗️ Niveau 1: Variables, Types & Fonctions

En Rust, les variables sont immutables par défaut. C'est la fondation de tout : le compilateur refuse de modifier ce qui n'a pas été explicitement déclaré comme mutable. Cela force une réflexion claire sur ce qui change et ce qui ne change pas.

Les types sont fortement typés mais souvent inférés. Rust déduit automatiquement le type à partir du contexte, sauf quand c'est ambigu. Les types primitifs (i32, f64, bool, &str) sont optimisés et très efficaces.

Les fonctions sont des citoyens de première classe : elles acceptent des paramètres typés, retournent une valeur (explicite ou implicite via l'expression finale), et peuvent être passées comme arguments. Le mot-clé fn est votre meilleur ami.

Concept clé: Immutabilité par défaut

let x = 5;           // x est immutable
let mut y = 10;     // y peut changer
y = 20;              // OK

fn add(a: i32, b: i32) -> i32 {
    a + b            // return implicite (pas de ;)
}

let result = add(3, 4);

Une variable shadowing permet de réutiliser un nom avec un nouveau type :

let x = 5;          // i32
let x = "hello";    // &str (shadowing, nouveau type)
⚠️ Pièges courants
  • Oublier le point-virgule: sans ;, l'expression devient la valeur retournée de la fonction.
  • Mutable par défaut: le compilateur refuse de modifier une variable non déclarée mut.
  • Types oubliés: parfois le compilateur ne peut pas inférer. Ajoutez l'annotation explicite : let x: i32 = 5;
→ Exercices: ex01, ex02, ex03, ex04

🔐 Niveau 2: Ownership & Borrowing (Le cœur de Rust)

C'est le concept le plus important en Rust. Chaque valeur a un propriétaire unique. Quand le propriétaire sort du scope, la mémoire est automatiquement libérée. Pas de garbage collector, pas de fuites mémoire.

Le système est basé sur 3 règles fondamentales : (1) chaque valeur a un propriétaire; (2) il ne peut y avoir qu'un propriétaire à la fois; (3) quand le propriétaire sort du scope, la valeur est détruite.

L'emprunt (borrowing) permet de passer une référence sans transférer la propriété. Il existe deux types : l'emprunt immutable (&T, plusieurs possibles) et l'emprunt mutable (&mut T, un seul à la fois). Le compilateur garantit qu'il n'y a jamais de data race.

Concept clé: Le Move (transfert de propriété)

let s1 = "hello".to_string();   // s1 possède la String
let s2 = s1;                    // move! s1 n'existe plus
// println!("{}", s1);  // ERREUR: s1 n'existe plus
println!("{}", s2);             // OK

Concept clé: Le Borrowing (l'emprunt)

let s = "hello".to_string();
print_len(&s);           // emprunt immutable, s existe toujours
println!("{}", s);        // OK

fn print_len(s: &String) {
    println!("{}", s.len());
}

Diagramme mémoire: Move vs Borrowing

// MOVE : Transfert de propriété s1 ─→ String { data: "hello", len: 5 } let s2 = s1; ↓ (s1 n'existe plus) s2 ─→ String { data: "hello", len: 5 } // BORROWING : Emprunt (référence) s ─→ String { data: "hello", len: 5 } ← &s ↑ (référence, s existe toujours)

Emprunt mutable vs immutable

let mut s = "hello".to_string();
modify(&mut s);              // emprunt mutable
println!("{}", s);             // s a été modifiée

fn modify(s: &mut String) {
    s.push_str(" world");
}

La règle du borrow checker

Vous ne pouvez pas avoir à la fois une référence mutable ET une référence immutable :

let mut v = vec![1, 2, 3];
let r1 = &v;              // emprunt immutable
let r2 = &v;              // OK, un autre emprunt immutable
// let r3 = &mut v;         // ERREUR: conflit!
println!("{:?}", r1);       // r1 et r2 sont utilisées ici
⚠️ Pièges courants
  • Move inattendu: passer une valeur à une fonction sans & la transfère. Utilisez &T pour garder la propriété.
  • Conflit de borrows: le borrow checker refuse souvent de compiler si vous mélangez & et &mut. Pensez au "scope" de l'emprunt : il finit quand la référence n'est plus utilisée.
  • Retourner une référence au scope local: impossible! Une fonction ne peut pas retourner &T si T est local. Utilisez les lifetimes ou retournez une valeur possédée.
→ Exercices: ex05, ex06, ex07

🎁 Niveau 3: Structs, Enums & Option

Les structs regroupent plusieurs champs typés dans une structure nommée. C'est votre outil pour modéliser des données complexes. Chaque champ peut avoir un type différent, et vous pouvez implémenter des méthodes sur la struct.

Les enums représentent une valeur qui peut être l'une de plusieurs variantes. Contrairement à beaucoup de langages, chaque variante peut contenir des données. Une enum est somme de types : ou A ou B ou C.

Option<T> est une enum built-in qui représente "peut-être une valeur ou rien". Au lieu d'utiliser null (dangereux), Rust force vous à gérer explicitement les deux cas avec le pattern matching.

Structs et implémentation

struct Person {
    name: String,
    age: u32,
}

impl Person {
    fn new(name: String, age: u32) -> Self {
        Person { name, age }
    }

    fn birthday(&mut self) {
        self.age += 1;
    }
}

let mut p = Person::new("Alice".to_string(), 30);
p.birthday();

Enums avec données

enum Message {
    Quit,
    Move { x: i32, y: i32 },
    Write(String),
    Color(u8, u8, u8),
}

let msg = Message::Write("hello".to_string());

match msg {
    Message::Quit => println!("Quit"),
    Message::Move { x, y } => println!("Move to {}, {}", x, y),
    Message::Write(s) => println!("Write: {}", s),
    Message::Color(r, g, b) => println!("RGB"),
}

Option<T>: Gérer l'absence de valeur

let x: Option<i32> = Some(5);
let y: Option<i32> = None;

match x {
    Some(val) => println!("Got {}", val),
    None => println!("Nothing"),
}

// Méthodes pratiques sur Option
let result = x.map(|v| v + 1);    // Some(6)
let val = y.unwrap_or(0);    // 0 (par défaut)
⚠️ Pièges courants
  • unwrap() sur None: .unwrap() panique si l'Option est None. Préférez .unwrap_or(default) ou pattern matching.
  • Oublier de pattern-matcher: une enum ne se "convertit" pas automatiquement. Utilisez match pour extraire les variantes.
  • Champs mutables: pour modifier un champ d'une struct, la struct elle-même doit être mut. Cela peut être verbose ; utilisez des builder patterns pour les gros modèles.
→ Exercices: ex08, ex09, ex10

🧬 Niveau 4: Traits & Génériques

Les traits définissent un ensemble de méthodes que d'autres types peuvent implémenter. C'est votre outil pour la polymorphie et l'abstraction. Un trait est un contrat : "si tu implémentes Display, tu dois avoir une méthode fmt()".

Les génériques permettent d'écrire du code qui fonctionne avec n'importe quel type. Une fonction générique fn foo<T>(x: T) est compilée une fois par type utilisé (monomorphisation).

Les trait bounds combinent les deux : vous pouvez dire "T doit implémenter Debug et Clone". Cela force le compilateur à vérifier que T a vraiment ces capacités.

Traits: Définir et implémenter

trait Drawable {
    fn draw(&self);
}

struct Circle { radius: f64 }

impl Drawable for Circle {
    fn draw(&self) {
        println!("Drawing circle");
    }
}

fn render(shape: &dyn Drawable) {
    shape.draw();
}

Génériques avec trait bounds

fn print_it<T: std::fmt::Debug>(val: T) {
    println!("{:?}", val);
}

struct Container<T> {
    item: T,
}

impl<T: Clone> Container<T> {
    fn clone_item(&self) -> T {
        self.item.clone()
    }
}
⚠️ Pièges courants
  • Trait objects et vtables: &dyn Trait implique une indirection et une recherche dynamique. C'est plus lent que la monomorphisation générique.
  • Oublier Clone ou Copy: les génériques ne savent pas si T peut être copié. Ajoutez T: Copy si vous en avez besoin.
  • Associated types vs génériques: un trait peut avoir des types associés (type Item;). Préférez-les pour simplifier l'API.
→ Exercices: ex11, ex12

🛡️ Niveau 5: Gestion d'Erreurs

Rust n'a pas d'exceptions. À la place, il utilise Result<T, E>, une enum qui peut être Ok(value) ou Err(error). Cela force à gérer explicitement les erreurs.

L'opérateur ? est sucre syntaxique : il "remonte" une erreur automatiquement. Si l'opération retourne Err, la fonction retourne Err immédiatement. Sinon, on continue avec Ok.

Panic est réservée aux situations vraiment irrécupérables (invariants violés, bugs). Pour les erreurs normales, retournez Result.

Result<T, E> et le match

fn divide(a: f64, b: f64) -> Result<f64, String> {
    if b == 0.0 {
        Err("Division by zero".to_string())
    } else {
        Ok(a / b)
    }
}

match divide(10.0, 2.0) {
    Ok(result) => println!("Result: {}", result),
    Err(e) => println!("Error: {}", e),
}

L'opérateur ? pour propager les erreurs

fn read_file(path: &str) -> Result<String, std::io::Error> {
    let content = std::fs::read_to_string(path)?;  // ? remonte l'erreur
    Ok(content)
}

// Sans ?, cela serait :
fn read_file_verbose(path: &str) -> Result<String, std::io::Error> {
    match std::fs::read_to_string(path) {
        Ok(content) => Ok(content),
        Err(e) => Err(e),
    }
}
⚠️ Pièges courants
  • unwrap() sur Err: comme avec Option, cela panique. Utilisez .unwrap_or(default) ou .expect("message") (panique avec un message).
  • ? en dehors d'une fonction Result: l'opérateur ? ne fonctionne que dans une fonction qui retourne Result (ou Option). Dans main(), utilisez .unwrap() ou ? (si main retourne Result).
  • Erreurs vagues: retourner String comme erreur perd les détails. Créez vos propres types d'erreur ou utilisez des crates comme thiserror.
→ Exercices: ex13, ex14

📦 Niveau 6: Collections, Itérateurs & Closures

Les collections (Vec, HashMap, HashSet) sont des conteneurs flexibles. Vec est un vecteur dynamique—un array qui grandit. HashMap stocke des paires clé-valeur.

Les itérateurs parcourent les collections de façon paresseuse. Ils sont très efficaces : vec.iter().map().filter().collect() est compilé en code optimisé sans allocations intermédiaires.

Les closures sont des fonctions anonymes qui capturent leur environnement. |x| x + 1 est une closure simple. Elles peuvent capturer par référence, par référence mutable, ou par déplacement.

Vec et opérations courantes

let mut v = vec![1, 2, 3];
v.push(4);
v.pop();          // retourne Some(4)
let first = v[0];  // accès direct

for item in &v {
    println!("{}", item);
}

Itérateurs: une programmation élégante

let v = vec![1, 2, 3, 4, 5];

// Chaîner les opérations
let result: Vec = v.iter()
    .filter(|x| *x > 2)
    .map(|x| x * 2)
    .collect();

// result = [6, 8, 10]

Closures: capturer l'environnement

let x = 5;
let add_x = |y| y + x;     // capture x par ref
println!("{}", add_x(3));   // 8

let mut counter = 0;
let mut inc = || {         // capture mut
    counter += 1;
    counter
};
inc();                     // 1
inc();                     // 2
⚠️ Pièges courants
  • Index hors limites: v[n] panique si n >= v.len(). Utilisez .get(n) qui retourne Option.
  • Capturage par déplacement: les closures capturent par référence par défaut, mais parfois elles doivent capturer par déplacement (move). Utilisez move || si nécessaire.
  • Itérateurs paresseux: v.iter().map() ne fait rien jusqu'à .collect(). Oublier collect() = pas de résultat!
→ Exercices: ex15, ex16, ex17

⏳ Niveau 7: Lifetimes (Les durées de vie)

Les lifetimes sont la façon de Rust d'exprimer "cette référence est valide tant que...". Elles ne changent pas le runtime—c'est une annotation pour le compilateur.

Pourquoi? Parce qu'une référence doit toujours pointer vers une données valide. Si vous retournez &String d'une fonction et que la String est détruite, vous avez undefined behavior. Les lifetimes forcent vous à penser à cela.

Dans la plupart des cas, Rust déduit les lifetimes automatiquement. Mais quand il y a ambiguïté—plusieurs références, une retournée—il vous demande de les annoter explicitement.

Concept clé: Lifetime annotations

// Deux références: laquelle est le lifetime du résultat?
fn longest<'a>(s1: &'a str, s2: &'a str) -> &'a str {
    if s1.len() > s2.len() { s1 } else { s2 }
}

// 'a signifie: la référence retournée est valide
// aussi longtemps que BOTH s1 et s2 sont valides

Diagramme: Les lifetimes en mémoire

// Les références doivent « vivre » au moins aussi longtemps // que la donnée qu'elles pointent ❌ INVALIDE: fn bad() -> &'static str { let s = "hello".to_string(); &s // ERREUR: s est destroyed après la fonction } ✅ VALIDE: fn good() -> String { let s = "hello".to_string(); s // OK: on retourne la valeur possédée } ✅ VALIDE (avec paramètre): fn borrow<'a>(s: &'a str) -> &'a str { s // OK: le lifetime de s est préservé }

Les 3 règles d'Elision (implicites)

// Ces trois fonctions sont équivalentes:

// Règle 1: une référence → lifetime implicite
fn foo(s: &str) -> &str   // OK, inféré

// Explicite:
fn foo<'a>(s: &'a str) -> &'a str

// Règle 2: &self → lifetime du self
struct S;
impl S {
    fn method(&self) -> &str  // OK, 'a := self
}
⚠️ Pièges courants
  • 'static vs autres lifetimes: 'static signifie "valide pendant toute la durée du programme". Les chaînes littérales ("hello") sont 'static. Autres références ont des lifetimes limités.
  • Retourner une référence au local: c'est l'erreur classique. Impossible! Si vous quittez la fonction, la valeur locale est détruite. Retournez une valeur possédée (String) ou une référence à un paramètre.
  • Trop d'annotations: Rust infère souvent. Si vous êtes tenté d'annoter chaque référence, pensez si vous pouvez retourner une valeur possédée à la place.
→ Exercices: ex18

🎯 Niveau 8: Smart Pointers

Un smart pointer est un pointeur qui fait plus qu'un pointeur brut. Il gère automatiquement la mémoire. Les plus courants : Box<T> (alloue sur le heap), Rc<T> (référence comptée), et RefCell<T> (emprunts à runtime).

Box<T> met une valeur sur le heap au lieu de la stack. C'est utile pour les types récursifs ou quand vous ne connaissez pas la taille. Quand la Box sort du scope, la mémoire est libérée.

Rc<T> permet la propriété partagée: plusieurs propriétaires, une seule donnée. Quand le dernier propriétaire s'en va, la donnée est détruite. C'est single-threaded; pour multi-threaded, utilisez Arc<T>.

RefCell<T> permet des emprunts mutables à runtime au lieu de compile-time. Utile quand le borrow checker refuse, mais attention: une violation au runtime panique!

Box: Allouer sur le heap

let b = Box::new(5);
println!("{}", *b);  // déréférencer

enum List {
    Cons(i32, Box<List>),  // récursif!
    Nil,
}

Rc: Propriété partagée

use std::rc::Rc;

let a = Rc::new(vec![1, 2, 3]);
let b = Rc::clone(&a);  // clone la ref, pas les données
let c = Rc::clone(&a);

// a, b, c partagent les mêmes données

RefCell: Emprunts à runtime

use std::cell::RefCell;

let cell = RefCell::new(5);
{
    let mut r = cell.borrow_mut();  // emprunt mutable
    *r += 1;
}  // l'emprunt se termine ici
println!("{}", *cell.borrow());  // 6
⚠️ Pièges courants
  • Rc vs Arc: Rc n'est pas thread-safe. Pour la concurrence, utilisez Arc<T>.
  • RefCell panics: si vous avez déjà emprunté mutablement et vous essayez de ré-emprunter, ça panique à runtime. C'est la "fuite" du borrow checker.
  • Rc<RefCell<T>> patterns: c'est courant pour les structures mutables partagées, mais peut devenir complexe. Réfléchissez si vous en avez vraiment besoin.
→ Exercices: ex19, ex20

⚡ Niveau 9: Concurrence

Rust rend la concurrence sûre par défaut. Le système de propriété et de traits garantit qu'il n'y a pas de data races. Les threads doivent utiliser Send (peut être envoyé) et Sync (peut être partagé).

std::thread::spawn crée un thread. L'expression closure doit capturer uniquement des valeurs Send, ou vous devez utiliser move. Les channels permettent la communication entre threads sans partage de mémoire.

Les mutexes (Mutex<T>) protègent une donnée partagée. Contrairement à beaucoup de langages, Rust force à verrouiller explicitement : vous ne pouvez pas oublier. Arc<Mutex<T>> combine la propriété partagée avec le protection.

Créer et joindre des threads

use std::thread;

let handle = thread::spawn(|| {
    println!("Hello from thread");
});

handle.join().unwrap();  // attendre la fin

Channels: Communication safe

use std::sync::mpsc;
use std::thread;

let (tx, rx) = mpsc::channel();

thread::spawn(move || {
    tx.send("message").unwrap();
});

let msg = rx.recv().unwrap();  // bloquer jusqu'à réception

Mutex: Partager et protéger

use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];

for _ in 0..10 {
    let c = Arc::clone(&counter);
    let handle = thread::spawn(move || {
        let mut num = c.lock().unwrap();
        *num += 1;
    });
    handles.push(handle);
}

for handle in handles {
    handle.join().unwrap();
}
⚠️ Pièges courants
  • Move closures: si vous envoyez une closure dans un thread, elle doit utiliser move pour capturer la propriété des variables.
  • Panics dans les threads: un panic dans un thread ne tue pas le programme principal. Capturez le résultat de join() pour détecter les panics.
  • Deadlocks: Rust ne les prévient pas. Si vous attendez A en tenant B, et un autre thread attend B en tenant A, c'est deadlock. Soyez attentif à l'ordre.
→ Exercices: ex21, ex22

🗄️ Niveau 10: Projets DB (Base de données)

Ces exercices appliquent tous les concepts précédents à la construction d'une base de données simple. Vous utiliserez structs pour modéliser les données, traits pour l'abstraction, gestion d'erreurs pour la robustesse, collections pour stocker, et peut-être concurrence pour les opérations simultanees.

Une DB typique a: (1) un modèle de donnée (structs/enums), (2) un storage (Vec, HashMap, fichier), (3) une API (insert, query, delete) qui retourne Result, (4) des validations pour garantir l'intégrité.

Les patterns clés : Builder pour la configuration, Traits pour l'abstraction du storage, Result pour les erreurs, et Rc/Mutex si plusieurs clients accèdent simultanément.

Structure simple d'une DB en mémoire

struct Database<T> {
    data: Vec<T>,
}

impl<T: Clone> Database<T> {
    fn new() -> Self {
        Database { data: vec![] }
    }

    fn insert(&mut self, item: T) {
        self.data.push(item);
    }

    fn query(&self, f: &dyn Fn(&T) -> bool) -> Vec<T> {
        self.data.iter()
            .filter(|x| f(x))
            .map(|x| x.clone())
            .collect()
    }
}

let mut db = Database::new();
db.insert("Alice");
let results = db.query(&|name| name.starts_with("A"));

Exemple avec Trait pour différents backends

trait Store<T> {
    fn save(&mut self, item: T) -> Result<(), String>;
    fn load(&self, id: u32) -> Result<Option<T>, String>;
}

struct MemoryStore<T> {
    data: Vec<T>,
}

impl<T> Store<T> for MemoryStore<T> {
    fn save(&mut self, item: T) -> Result<(), String> {
        self.data.push(item);
        Ok(())
    }

    fn load(&self, id: u32) -> Result<Option<T>, String> {
        Ok(self.data.get(id as usize).cloned())
    }
}
⚠️ Pièges courants
  • Transactions ignorées: une DB sans transactions peut être corrompue si un insert échoue à mi-chemin. Pensez à la cohérence des données.
  • Pas d'index: une simple Vec est O(n) pour les recherches. Si la DB grandit, vous avez besoin d'index (HashMap).
  • Concurrence naïve: Arc<Mutex<DB>> fonctionne mais se serialize tout. Pour une vraie DB, vous avez besoin de concurrence plus fine (read-write locks, sharding).
→ Exercices: ex23, ex24, ex25

enum Color { Red, Blue } match c { Color::Red => {} Color::Blue => {} }

Option<T>

let x: Option<i32> = Some(5); x.unwrap(); x.map(|v| v + 1); x.unwrap_or(0);

fn foo() -> Result<i32, String> Ok(42) Err("error".into())

Itérateurs

let v = vec![1, 2, 3]; v.iter() .filter(|x| *x > 1) .map(|x| x * 2) .collect()

Closures

Traits

Génériques
